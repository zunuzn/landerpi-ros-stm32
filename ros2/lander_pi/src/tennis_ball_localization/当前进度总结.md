# 远处网球定位程序阶段技术进度说明

## 1. 当前目标

当前阶段目标不是直接完成整车导航，而是先把网球视觉定位链路在 Windows 上验证清楚：

```text
RGB 图像
  -> YOLO 网球检测
  -> 多目标稳定层
  -> Depth 深度对齐
  -> 相机坐标系 XYZ
```

也就是说，目前输出的是**网球相对于相机的三维坐标**，还不是小车坐标系，也不是 SLAM 地图坐标。

## 2. 当前整体架构

目前代码分成几层：

```text
DeptrumScope 保存数据
  -> 输入层：读取/监控 Rgb + Depth 文件
  -> 检测层：YOLO 检测网球 2D 框
  -> 稳定层：给多个球维护 track_id 并平滑 bbox
  -> 深度层：从 depth 图中取深度并计算 camera XYZ
  -> 输出层：显示窗口、CSV、调试图
```

核心文件：

```text
src/tennis_ball_detector.py          YOLO 检测封装
src/stable_tennis_ball_tracker.py    多球稳定层
src/tennis_ball_depth_locator.py     深度定位/坐标换算
scripts/test_deptrum_saved_depth.py      离线保存数据测试
scripts/watch_deptrum_saved_depth.py     监控 DeptrumScope 保存目录，模拟实时输入
```

## 3. 数据输入层

当前没有直接调用 Deptrum SDK，而是使用 DeptrumScope 软件保存的数据。

DeptrumScope 保存目录结构类似：

```text
Aurora930_xxx/
  Rgb.csv
  Depth.csv
  Rgb/
    Rgb_1_1786014201990.jpg
    Rgb_2_1786014202090.jpg
  Depth/
    Depth_1_1786014201990.png
    Depth_2_1786014202090.png
```

程序按 `index + timestamp` 匹配 RGB 和 Depth：

```text
Rgb.csv   -> index, timestamp
Depth.csv -> index, timestamp

Rgb_1_xxx.jpg 对应 Depth_1_xxx.png
```

当前实现了两种输入方式：

1. 离线一次性读取：

```text
scripts/test_deptrum_saved_depth.py
```

2. 持续监控保存目录，模拟实时相机输入：

```text
scripts/watch_deptrum_saved_depth.py
```

目录监控版会不断扫描 `Rgb.csv` 和 `Depth.csv`，只处理还没处理过的新帧。

## 4. YOLO 检测层

当前使用现成网球检测模型：

```text
模型文件：models/tennis_ball_best.pt
模型结构：YOLOv8n
类别数：1
参数量：3,011,043
```

检测层输入：

```text
RGB 图像，OpenCV BGR ndarray
```

检测层输出每个球：

```text
class_id
confidence
bbox = [x1, y1, x2, y2]
center = [center_x, center_y]
width
height
```

其中 `bbox` 是图像像素坐标：

```text
x1, y1：检测框左上角
x2, y2：检测框右下角
center_x, center_y：检测框中心点
```

## 5. 稳定层逻辑

稳定层文件：

```text
src/stable_tennis_ball_tracker.py
```

它的作用不是选择主目标，也不是决定小车先去哪一个球。  
它只做感知层稳定输出：

```text
每一帧 YOLO 检测结果
  -> 分配 track_id
  -> 平滑 bbox / center
  -> 短时间保留丢失目标
  -> 输出所有球
```

当前匹配方式：

```text
根据检测框中心点距离做最近邻匹配
```

如果当前帧某个检测框离已有 track 足够近，就认为是同一个球。  
默认匹配距离：

```text
max_match_distance = 60 px
```

平滑方式：

```text
EMA 指数滑动平均
smooth_alpha = 0.65
```

稳定层输出字段：

```text
track_id
class_id
confidence
bbox
center
center_x
center_y
width
height
valid
age
hits
miss_count
```

关键字段解释：

```text
valid=True
```

表示当前帧 YOLO 真实检测到了这个球。这个结果可以拿去和 depth 图对齐。

```text
valid=False
```

表示当前帧 YOLO 没检测到，只是稳定层短暂保留的预测结果。这个结果不用于深度定位。

当前稳定层还没有加：

```text
hits >= N 才输出距离
```

所以现在只要 `valid=True`，就会尝试深度定位。  
如果后面希望“连续稳定检测 3 帧后才输出 XYZ”，可以增加 `min_hits` 门槛。

## 6. 深度定位层

深度定位文件：

```text
src/tennis_ball_depth_locator.py
```

深度定位输入：

```text
稳定层输出的 track
Depth 图
相机内参 fx/fy/cx/cy
```

当前默认使用 Aurora930 的估计内参：

```text
fx = 448.62
fy = 471.17
cx = 319.50
cy = 199.50
```

这些值来自：

```text
分辨率：640x400
水平视场角：71°
垂直视场角：46°
```

注意：这是估计内参，不是相机官方标定内参。后续 ROS 阶段应该从 `/camera_info` 中读取真实内参。

### 深度取样

当前默认取样点：

```text
sample_point = center
```

即使用检测框中心点：

```text
u = center_x
v = center_y
```

深度取样不是只取单个像素，而是取中心附近小窗口：

```text
patch_radius = 3
窗口大小 = 7x7
```

处理逻辑：

```text
1. 在 depth 图中取 7x7 patch
2. 过滤 depth=0 的无效像素
3. 对剩余有效深度取中位数
4. 如果中心 patch 没有有效深度，再尝试整个 bbox 区域
```

### 坐标换算

Depth 原始值按毫米处理：

```text
depth_scale = 0.001
Z = depth_raw * depth_scale
```

像素坐标转相机坐标公式：

```text
X = (u - cx) * Z / fx
Y = (v - cy) * Z / fy
Z = depth
```

输出坐标含义：

```text
camera_x_m：相机右侧为正
camera_y_m：相机下方为正
camera_z_m：相机前方为正
```

这套坐标是相机坐标系，不是小车坐标系。

## 7. 当前输出

目录监控版输出：

```text
outputs/deptrum_watch/detections_with_depth.csv
outputs/deptrum_watch/debug_frames/
```

CSV 每一行表示：

```text
某一帧中的一个 track
```

主要字段按类别分：

### 检测字段

```text
confidence
x1 / y1 / x2 / y2
center_x / center_y
```

表示 YOLO 检测结果。

### 稳定字段

```text
track_id
valid
age
hits
miss_count
```

表示稳定层状态。

### 深度字段

```text
sample_point
sample_x / sample_y
depth_raw_median
depth_m
depth_samples
depth_aligned
```

其中：

```text
depth_aligned=True
```

表示成功从 depth 图取到了有效深度。

### 三维坐标字段

```text
camera_x_m
camera_y_m
camera_z_m
```

表示网球在相机坐标系下的三维坐标，单位米。

## 9. 当前技术边界

目前还没有完成以下内容：

1. 没有直接调用 Deptrum SDK 实时取流
   - 当前是监控 DeptrumScope 保存目录，模拟实时输入。

2. 没有使用真实相机标定内参
   - 当前内参由分辨率和视场角估算。
   - ROS 阶段应从 `CameraInfo` 获取真实内参。

3. 没有转换到小车坐标系
   - 当前输出是 `camera_x_m / camera_y_m / camera_z_m`。
   - 后续需要相机安装外参，转换到 `base_link`。

4. 没有转换到地图坐标系
   - 还需要结合 SLAM 位姿，把 `base_link` 坐标转成 `map` 坐标。

5. 稳定层还没有“最小命中帧数”门槛
   - 现在 `valid=True` 就会尝试测距。
   - 如果需要更严格，可以加 `min_hits=3`。

6. Aurora930 深度不适合 25m 远距离测距
   - Aurora930 资料中的工作距离约为 30cm 到 300cm。
   - 远距离网球阶段更适合做图像发现，近距离再用 depth 精定位。

## 12. 非 4K RGB 相机的远处网球可发现距离估算

如果不使用 4K RGB，而是使用 Gemini 335L / D455 这类 `1280x800` RGB，相机水平视场角约 `90°`，网球直径按 `6.7cm` 估算：

```text
网球像素直径 ≈ 1280 × 0.067 / (2 × 距离 × tan(90° / 2))
             ≈ 42.9 / 距离
```

|   距离 | 网球直径大约占多少像素 | 判断              |
| ---: | ----------: | --------------- |
|  3 m |     约 14 px | 比较可识别           |
|  4 m |     约 11 px | 有工程可行性          |
|  5 m |    约 8.6 px | 勉强可用，需要专用模型和稳定层 |
|  7 m |    约 6.1 px | 很不稳定，只能实验性发现    |
| 10 m |    约 4.3 px | 基本不可靠           |
| 15 m |    约 2.9 px | 基本识别不到          |
| 25 m |    约 1.7 px | 不能指望 YOLO 识别    |

阶段性结论：

```text
可靠识别：3~5 m
勉强发现：5~7 m
超过 10 m：基本不可靠
25 m：不现实
```

因此，如果只使用 Gemini 335L 或 D455 的 `1280x800` RGB，实际策略应该是：

```text
先依靠 SLAM / 导航接近目标区域
进入约 5 m 范围后再可靠识别网球
识别后再用 RGB-D 输出相机坐标系 XYZ
```
